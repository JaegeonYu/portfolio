SQLP 스터디 운영 시스템

SQLP를 취득한 뒤, 스터디원 두 명과 SQL 튜닝 스터디를 시작하면서 멘토를 맡게 되었습니다. 매주 실습 문제를 내고 풀이를 확인해야 했는데, 이걸 사람이 직접 하기에는 손이 많이 갔습니다. 그래서 문제 공개부터 채점, 진행 상황 정리까지 자동으로 돌아가는 시스템을 만들었습니다.

처음에 정한 조건

만들기 전에 세 가지를 먼저 정했습니다.

  1. 스터디원은 브라우저만 쓸 수 있어야 합니다. git이나 DB를 따로 설치하지 않아도 참여할 수 있어야 했습니다.
  2. 운영비는 0원이어야 합니다. 개인이 꾸리는 스터디라 서버 비용을 계속 낼 수는 없었습니다.
  3. 제출한 SQL과 정답은 공개하지 않습니다. 다만 각자 얼마나 진행했는지와 쓴 글은 함께 볼 수 있게 하고 싶었습니다.

그래서 GitHub의 이슈와 Actions, Oracle Cloud의 무료 DB를 조합하기로 했습니다. 저장소는 채점 기록을 담는 비공개 저장소(sqlp-judge)와, 공개해도 되는 기록만 모은 공개 저장소(sqlp-archive)로 나눴습니다.

공개 사이트 열람

스터디원이 GitHub 이슈 양식에 SQL을 붙여 넣고 제출하면, GitHub Actions가 그 SQL을 Oracle Cloud의 DB에서 실행합니다. 결과가 정답과 같은지, 그리고 읽은 블록 수가 목표 이하인지를 보고 통과 여부를 이슈 댓글로 남깁니다.

주차가 시작되면 그 주의 문제가 열리고, 스터디원마다 할 일 목록과 포스팅 초안 PR이 자동으로 만들어집니다. 스터디원은 초안에 글만 쓰면 되고, 제가 리뷰해서 머지하면 공개 사이트에 올라갑니다. 진행률도 같은 흐름으로 매번 다시 계산되어 사이트에 반영됩니다.

모든 자동화는 비공개 저장소의 Actions에서 돌아갑니다. 채점이 끝나면 공개해도 되는 데이터만 골라 공개 저장소로 보내고, 공개 저장소는 그 데이터와 머지된 포스팅으로 사이트를 다시 만듭니다. 반대로 공개 저장소에서 포스팅이 머지되면(점선), "진행률을 다시 계산해 달라"는 요청만 보낼 수 있는 별도의 GitHub App을 통해 비공개 저장소에 알립니다.

DB 계정은 일부러 셋으로 나눴습니다. 문제 데이터는 STUDY 계정이 갖고, 스터디원의 SQL은 그 테이블을 읽기만 할 수 있는 GRADER_RUN 계정으로 실행합니다. 읽은 블록 수는 실행 통계 조회 권한만 있는 GRADER_STATS 계정이 따로 읽습니다. 누가 어떤 SQL을 내더라도 데이터를 바꾸거나 다른 사람의 기록을 볼 수 없게 하려는 것이었습니다.

만들면서 부딪힌 문제

실행 시간으로는 공정하게 채점할 수 없었습니다

처음에는 SQL이 빨리 끝나면 통과시키는 방식을 생각했습니다. 그런데 같은 SQL을 여러 번 돌려 보니, 캐시에 데이터가 올라와 있는지와 그 순간 DB가 얼마나 바쁜지에 따라 실행 시간이 매번 달랐습니다. 이대로라면 같은 답을 내도 언제 냈느냐에 따라 통과와 실패가 갈릴 수 있었습니다.

그래서 SQL이 읽은 블록 수(Buffers)를 기준으로 바꿨습니다. 블록 수는 실행계획이 같으면 거의 같은 값이 나오고, SQLP에서 튜닝을 평가하는 관점도 결국 "얼마나 적게 읽었는가"입니다. 실행 시간은 통과 기준에서 빼고, 너무 오래 걸리는 SQL을 끊는 제한으로만 남겼습니다.

로컬에서 정한 목표값이 클라우드에서 맞지 않았습니다

처음에는 제 PC의 Docker Oracle에서 정답 SQL을 돌려 보고 목표 블록 수를 정했습니다. 그런데 같은 SQL을 Oracle Cloud에서 실행하니 로컬에서는 10블록이던 것이 19블록이 나왔습니다. 버전과 설정이 다른 DB라 같은 SQL도 읽는 양이 달랐던 것입니다.

실제 채점은 클라우드에서 하기 때문에, 목표값은 모두 클라우드에서 잰 값으로 다시 잡았습니다. 이 일을 계기로 권한, 네트워크, 동시 제출 같은 부분도 로컬이 아닌 실제 클라우드 환경에서 하나씩 확인한 뒤에 스터디를 시작했습니다.

힌트가 무시됐는데도 통과로 나왔습니다

한 스터디원이 FULL 힌트를 줬는데 실행계획이 전혀 바뀌지 않았다며 질문을 남겼습니다. 확인해 보니 힌트 문법이 틀려 있었습니다. Oracle은 틀린 힌트를 오류 없이 그냥 무시하는데, 마침 옵티마이저가 고른 계획이 목표를 넘어서 통과로 판정되고 있었습니다.

스터디원은 의도한 방식으로 풀었다고 생각하는데 실제로는 다른 방식으로 실행된 것이라, 통과로 두면 안 된다고 판단했습니다. Oracle 19c는 실행계획 정보에 힌트가 어떻게 처리됐는지를 함께 기록해 주기 때문에, 채점할 때 이 정보를 읽어 무시된 힌트를 댓글에 보여 주고 해당 제출은 반려하도록 바꿨습니다.

Hint Report (identified by operation id / Query Block Name / Object Alias):
   1 -  SEL$1 / E@SEL$1
         E -  FULL(e employees_dept_ix)  ← Syntax error

공개 사이트에 무엇을 보여 줄지 정해야 했습니다

스터디원의 진행률과 글은 공개하고 싶었지만, GitHub 계정이나 제출한 SQL, 정답까지 드러나면 안 됐습니다. 그래서 공개 저장소로 보내는 데이터는 채점 저장소에서 미리 걸러서 만들고, 작성자와 리뷰어는 GitHub 계정 대신 닉네임으로만 표시했습니다.

사람이 실수로 넣을 수도 있어서, 사이트를 만들 때 공개하면 안 되는 항목이 섞여 있는지 한 번 더 검사하고, 섞여 있으면 배포가 멈추도록 했습니다.

돌아보며

가장 크게 남은 건, 로컬에서 잘 되던 것도 실제 환경에서 다시 확인해야 한다는 점입니다. 채점 기준을 정할 때도 무엇이 매번 같은 값으로 측정되는지부터 확인해야 했습니다.

무시된 힌트처럼 오류 없이 지나가는 문제는 사용자가 알아채기 어렵습니다. 그런 부분은 시스템이 대신 드러내 줘야 한다는 것도 이번에 배웠습니다. 스터디는 지금도 진행 중이고, 스터디원들이 실제로 쓰면서 남기는 질문을 보고 계속 고쳐 나가고 있습니다.
